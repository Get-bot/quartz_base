## 이 장에서 남은 것

- 타입 뒤 `?` 하나로 **NPE가 실행 중 예외에서 컴파일 오류로 옮겨 온다.** 타입은 기본이 널이 될 수 없는 쪽이고, 널이 될 수 있는 값에는 메서드 호출·대입·전달이 막힌다.
- `?.`은 null이면 호출을 건너뛰고 null을 돌려주고, `?:`는 그 null 자리에 기본값을 댄다. `return`·`throw`도 식이라 **`?: return`·`?: throw`로 null일 때 함수를 빠져나간다.**
- `!!`는 검사가 아니라 **컴파일러에게 하는 약속**이다. 틀리면 NPE가 그대로 난다. 책임은 쓴 쪽에 있다.
- 자바에서 온 값은 널 정보가 없는 **플랫폼 타입**이다. 널로 다룰지는 코틀린 쪽에서 정하고, 컴파일러는 어느 쪽을 골라도 말리지 않는다.

## 널이 될 수 있는지를 타입에 적으면 NPE가 컴파일 오류가 된다

- **타입** — 가능한 값의 집합과, 그 값들에 수행할 수 있는 연산의 집합
- **널이 될 수 있는 타입** — 타입 이름 뒤에 물음표를 붙인 타입. `String?` 변수나 프로퍼티에는 `null` 참조를 저장할 수 있다
- **널이 될 수 없는 타입** — 물음표가 없는 타입. 모든 타입은 기본적으로 이쪽이다

타입을 값과 연산의 집합으로 보면 자바의 문제가 보인다. 자바의 `String` 변수에는 문자열도 `null`도 들어가는데, `length()`는 문자열에만 통한다. 같은 타입 안에서 값마다 쓸 수 있는 연산이 다르고 그 차이는 실행해 봐야 NPE로 드러난다. 코틀린은 `String`과 `String?`을 다른 타입으로 갈라서 이 차이를 타입에 올린다. **`null`이 들어올 수 있는지가 타입의 일부다.**

함수에 `null`이 들어오는 길은 둘이다. `null` 리터럴을 직접 넘기는 것, 그리고 실행 시점에 `null`이 될 수 있는 변수나 식을 넘기는 것. `fun strLen(s: String) = s.length`는 두 길을 다 컴파일 시점에 막는다. 대신 널이 될 수 있는 값에는 컴파일러가 세 가지를 금지한다.

- 메서드를 직접 호출할 수 없다
- 널이 될 수 없는 타입의 변수에 대입할 수 없다. `var y: String = x`는 `Initializer type mismatch`
- 널이 될 수 없는 타입의 파라미터를 받는 함수에 넘길 수 없다. `strLen(x)`는 컴파일되지 않는다

```kotlin
fun strLenNull(s: String?) = s.length

// Only safe (?.) or non-null asserted (!!.) calls are allowed on a nullable receiver of type 'String?'.
```

오류 메시지가 이미 출구 두 개를 알려 준다. 안전한 호출 `?.`이나 널 아님 단언 `!!.`만 된다. 세 번째 출구는 `null`과 직접 비교하는 것이다. 한 번 비교하고 나면 컴파일러가 그 결과를 기억해서 `null`이 아님이 확실한 영역에서는 그 값을 널이 될 수 없는 타입처럼 쓰게 해 준다(스마트 캐스트). 자바라면 실행 중에 NPE로 알았을 실수가 코틀린에서는 컴파일되지 않는다.

## `?.`은 null이면 호출을 건너뛰고 `?:`는 그 자리에 기본값을 댄다

- **안전한 호출 연산자 `?.`** — `null` 검사와 메서드 호출을 한 연산으로 한다. 값이 `null`이 아니면 일반 메서드 호출처럼 작동한다. `null`이면 호출을 무시하고 결괏값이 `null`이 된다. 프로퍼티를 읽거나 쓸 때도 쓴다
- **엘비스 연산자 `?:`** — 첫 번째 값이 `null`이 아니면 그 값이 결과고 `null`이면 두 번째 값이 결과다. `null` 대신 쓸 기본값을 정한다

`?.`의 결과는 여전히 널이 될 수 있는 타입이다. `s?.uppercase()`는 `String?`이라 `printAllCaps(null)`은 `null`을 찍는다. `null`을 없애는 게 아니라 **`null`이 식을 따라 흘러가게 둔다.** 그래서 널이 될 수 있는 중간 객체가 여럿인 객체 그래프에서 `?.`을 연쇄할 수 있다.

```kotlin
class Company(
    val name: String,
    val address: Address?,
)

class Person(
    val name: String,
    val company: Company?,
)

fun Person.countryName(): String {
    val country = company?.address?.country // 안전한 호출 연산자를 여러 개 연쇄해 사용
    return country ?: "Unknown"
}
```

회사도 주소도 없을 수 있다. `Person("Someone", null)`이면 `company?`에서 바로 `null`이 되고 뒤의 `address`·`country`는 읽지도 않는다. 흘러온 `null`을 마지막에 `?:`가 받아 `Unknown`으로 바꾼다. 두 줄은 `company?.address?.country ?: "Unknown"` 식 하나로 접힌다. `?.`이 `null`을 끝까지 실어 나르고 `?:`가 끝에서 받는 짝이다. 프로퍼티 하나를 읽을 때도 같다. `employee.manager?.name`은 매니저가 없는 `ceo`면 `null`, `ceo`를 매니저로 둔 `developer`면 `Boss`다.

`return`과 `throw`도 식이라 `?:`의 오른쪽에 들어간다.

```kotlin
fun printShippingLabel(person: Person) {
    val address = person.company?.address ?: throw IllegalArgumentException("No address")
    with(address) {
        println(streetAddress)
        println("$zipCode $city $country")
    }
}
```

주소가 없으면 첫 줄에서 예외를 던지고 끝난다. 그래서 `address`는 `Address?`가 아니라 `Address`고 `with` 블록 안에서는 `?.` 없이 프로퍼티를 읽는다. **`?: throw`·`?: return`은 null인 경우를 입구에서 끊고 그 아래 코드는 null을 신경 쓰지 않는다.**

## `as?`는 실패한 캐스트를 null로 바꾸고, `?.let`은 null이 아닐 때만 블록을 돈다

- **`as?`** — 값을 지정한 타입으로 변환한다. 대상 타입으로 바꿀 수 없으면 예외를 던지지 않고 `null`을 돌려준다. `as`라면 `ClassCastException`이 날 자리다
- **`let`** — 자신의 수신 객체를 인자로 전달받은 람다에 넘긴다. `?.`과 함께 쓰면 수신 객체가 `null`이 아닐 때만 람다가 불린다

둘 다 결과가 `null`로 이어져서 앞 절의 연산자와 맞물린다. `as?`는 `?:`와 붙여 쓰는 게 정석이다.

```kotlin
    override fun equals(other: Any?): Boolean {
        val otherPerson = other as? Person2 ?: return false
        return firstName == otherPerson.firstName && lastName == otherPerson.lastName
    }
```

`other`가 `Person2`가 아니면 `as?`가 `null`을 내고 `?:`가 `return false`로 함수를 끝낸다. 타입 검사, 캐스트, 실패 시 반환이 한 줄이다. 다음 줄의 `otherPerson`은 이미 `Person2`라 프로퍼티를 바로 읽는다.

`let`은 널이 될 수 있는 값을 널이 될 수 없는 파라미터에 넘길 때 쓴다.

```kotlin
val email: String? = "foo@bar.com"
sendEmailTo(email) // ERROR
// Argument type mismatch: actual type is 'String?', but 'String' was expected.
email?.let { sendEmailTo(it) }
```

`sendEmailTo`는 `String`을 받으니 `String?`인 `email`을 그대로 넘기면 첫 절의 세 번째 금지에 걸린다. `email?.let { ... }`은 `email`이 `null`이면 `let` 호출 자체가 건너뛰어지고, 아니면 `it`이 `String`으로 람다에 들어간다. **null인지 검사하고, 결과를 변수에 담고, 그걸로 호출하는 일이 식 하나로 끝난다.** 널이 될 수 있는 타입의 객체를 널이 될 수 없는 타입으로 바꾸는 효과다.

## 컴파일러가 모르는 '널 아님'은 `!!`와 `lateinit`으로 내가 보증한다

- **널 아님 단언 `!!`** — 어떤 값이든 널이 될 수 없는 타입으로 강제로 바꾼다. 실제로 `null`인 값에 쓰면 NPE가 난다
- **지연 초기화 프로퍼티 `lateinit`** — 널이 될 수 없는 프로퍼티를 생성자 밖에서 나중에 초기화하겠다고 표시하는 변경자

컴파일러가 null이 아님을 증명하지 못하지만 나는 아는 자리가 있다. 거기서 `?.`을 늘어놓는 대신 `!!`로 단언한다.

```kotlin
fun ignoreNulls(str: String?) {
    val strNotNull: String = str!!
    println(strNotNull.length)
}

ignoreNulls(null) // ERROR
```

`str!!` 다음부터 `strNotNull`은 `String`이라 `length`를 바로 부른다. 컴파일러는 `!!`를 믿고 넘어가고 `null`이 들어오면 그 자리에서 NPE가 난다. **`!!`는 검사가 아니라 약속이고, 틀린 약속의 책임은 쓴 쪽에 있다.** 그래도 쓰는 자리는 있다.

- 테스트 코드
- 스마트 캐스트의 한계를 넘을 때 — 가변 프로퍼티는 `null` 비교와 사용 사이에 값이 바뀔 수 있어서 컴파일러가 스마트 캐스트를 해 주지 않는다
- 스프링 생명주기상 초기화가 100% 보장된 상태

`lateinit`은 같은 약속을 선언에서 한다. 코틀린은 생성자에서 모든 프로퍼티를 초기화하라고 하고 널이 될 수 없는 타입이면 널이 아닌 값으로 채우라고 한다. 테스트의 `setUp`처럼 별도 메서드에서 초기화하는 프로퍼티는 이 규칙에 걸려서 `?`를 붙이고 쓸 때마다 `?.`이나 `!!`를 달아야 한다.

```kotlin
class MyTest {
    private lateinit var myService: MyService // 초기화하지 않고 널이 아닌 프로퍼티 선언

    fun setUp() {
        myService = MyService()
    }
}
```

`lateinit`을 붙이면 `myService`는 `MyService` 타입 그대로 두고 초기화만 `setUp`으로 미룬다. 값을 나중에 넣어야 하니 `var`이다. 초기화하기 전에 읽으면 NPE 대신 초기화되지 않았다는 예외가 난다. `!!`가 쓰는 자리에서 하는 약속이면 `lateinit`은 선언에서 하는 약속이다.

## `?.` 없이 부르는 확장과 `?` 없이 쓰는 `T`도 null을 받는다

- **널이 될 수 있는 타입에 대한 확장** — 수신 객체 타입이 널이 될 수 있는 타입인 확장 함수. `null`을 수신 객체로 받아 안에서 처리한다. 그 안에서는 `this`가 `null`일 수 있다
- **타입 파라미터의 널 가능성** — 타입 파라미터 `T`는 이름 끝에 물음표가 없어도 널이 될 수 있는 타입이다
- **널이 될 수 없는 타입 상계** — `<T : Any>`처럼 상계를 주면 `T`가 널이 아님을 확실히 하고 널이 될 수 있는 값을 거부한다

```kotlin
fun verifyUserInput(input: String?) {
    if (input.isNullOrBlank()) {
        println("Input cannot be blank")
    }
}
```

`input`은 `String?`인데 `?.` 없이 `.`으로 부른다. `isNullOrBlank`가 널이 될 수 있는 타입에 대한 확장이라서다. 수신 객체가 null이 아니라고 호출하는 쪽이 보장하는 대신, 함수가 `null`을 받고 안에서 처리한다. **이건 확장 함수만 된다.** 멤버 호출은 객체 인스턴스를 통해 디스패치되니 인스턴스가 `null`인지 검사할 틈이 없다.

```kotlin
fun <T> printHashCode(t: T) {
    println(t?.hashCode()) // t가 널이 될 수 있으므로 안전한 호출을 써야한다.
}

printHashCode(null) // T의 타입은 Any?로 추론된다.
```

반대 방향의 함정이 `T`다. 물음표가 없어서 널이 될 수 없어 보이지만 `printHashCode(null)`이면 `T`가 `Any?`로 추론되고, 그래서 안에서 `t?.hashCode()`를 써야 한다. 막으려면 `fun <T : Any> printHashCodeAny(t: T)`처럼 널이 될 수 없는 상계를 준다. 그러면 안에서 `t.hashCode()`를 바로 부르고 `printHashCodeAny(null)`은 컴파일되지 않는다.

## 자바에서 온 타입은 널 정보가 없는 플랫폼 타입이고, 판단은 코틀린 쪽이 한다

- **플랫폼 타입** — 코틀린이 널 관련 정보를 알 수 없는 타입. 널이 될 수 있는 타입으로 처리해도 되고 널이 될 수 없는 타입으로 처리해도 된다
  - 플랫폼 타입의 값에 널 안전성 검사를 중복으로 해도 아무 경고도 없다
  - 코틀린에서 선언할 수는 없다. 자바 코드에서 가져온 타입만 플랫폼 타입이 된다
- **자바 메서드를 오버라이드할 때** — 파라미터와 반환 타입을 널이 될 수 있는 타입으로 선언할지, 널이 될 수 없는 타입으로 선언할지 정해야 한다

첫 절의 보장은 코틀린이 널 가능성을 아는 타입까지만이다. 자바 메서드가 돌려준 `String`은 `null`일 수도 아닐 수도 있는데, 코틀린은 그걸 모르니 `String`으로 다루든 `String?`으로 다루든 막지 않는다. 널이 될 수 없는 쪽으로 다뤘는데 실제로 `null`이 오면 예외는 다시 실행 시점에 난다. **자바 경계에서는 컴파일러가 하던 판단을 내가 한다.**

상속도 같다. 자바 인터페이스의 메서드를 코틀린에서 구현하면 시그니처의 널 가능성을 선언으로 정해야 한다. 널이 될 수 없는 타입으로 선언한 파라미터에는 코틀린 컴파일러가 널이 아님을 검사하는 단언을 넣는다. 자바 코드가 거기에 `null`을 넘기면 그 자리에서 예외가 난다.

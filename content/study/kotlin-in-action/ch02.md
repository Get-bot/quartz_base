## 이 장에서 남은 것

- 루프와 대입만 빼면 **제어 구조가 전부 식이다.** if·when·try·throw를 값 자리에 그대로 놓고, 그래서 함수 본문도 등호 한 줄로 끝난다.
- `val`은 참조를 잠그지 **객체를 잠그지 않는다.** `var`는 반대로 값은 바뀌어도 타입은 못 바꾼다.
- 프로퍼티는 필드가 아니라 **접근자 선언이다.** 읽으면 getter, 대입하면 setter가 불리고, 저장하지 않고 읽을 때마다 계산하는 프로퍼티도 있다.
- 스마트 캐스트는 **값이 안 바뀐다고 컴파일러가 확신할 때만** 걸린다. 프로퍼티가 접근자 호출이라서 `var`나 커스텀 getter에는 안 걸린다.
- 체크 예외가 없다. 무엇을 잡을지는 **호출하는 쪽이 정하고**, 컴파일러는 더 이상 알려주지 않는다.

## 자바가 의례로 요구하던 코드가 문법에서 빠진다

첫 예제 `fun main() { println("Hello, world!") }`에서 이미 자바와 갈린다.

- **`fun`** — 함수는 `fun`으로 선언한다. 파라미터는 `이름: 타입` 순서이고 반환 타입은 닫는 괄호 뒤에 콜론을 찍고 적는다
- **최상위 함수** — 함수를 클래스 안에 넣지 않아도 된다. 파일 맨 바깥에 바로 둔다
- **인자 없는 `main`** — 진입점이 `args`를 받지 않아도 된다
- **표준 라이브러리 래퍼** — `println`은 `System.out.println`을 감싼 코틀린 함수다. 자바 표준 라이브러리 위에 짧은 이름을 얹는다
- **세미콜론 생략** — 줄 끝에 `;`를 쓰지 않는다
- **문자열 템플릿** — `"Hello, $name!"`처럼 변수 앞에 `$`를 붙이면 문자열 안에서 그 값을 쓴다. 식은 `${name.length}`처럼 중괄호로 감싸고 `$` 문자 자체는 `\$`로 이스케이프한다
- **`public` 기본값** — 가시성 지정자를 생략하면 `public`이다. `class Person(val name: String)` 한 줄이 자바의 필드·생성자·getter를 대신한다

최상위 함수의 이득은 2장이 아니라 3장에서 나온다. 자바에서 정적 메서드만 모아두던 유틸리티 클래스가 필요 없어진다. 함수는 클래스가 아니라 패키지에 속하고 다른 패키지에서는 클래스처럼 이름으로 `import`한다.

문자열 템플릿은 변수 뒤에 글자가 바로 붙으면 어디까지가 이름인지 흐려진다. 한글도 식별자에 쓰는 문자라 `$name님`은 `name님`이라는 변수를 찾는다. **변수 하나라도 `${}`로 감싸두면 이 문제가 없다.** 컴파일 결과는 타깃 JVM에 따라 다르다. 9 미만이면 `StringBuilder` 연결이고 9 이상이면 `invokedynamic`으로 `StringConcatFactory`를 부른다 — 템플릿 뼈대(`"Name: \u0001, Age: \u0001"`)와 인자를 런타임에 넘기고 연결 전략은 JVM이 고른다.

패키지 규칙은 자바와 같다. 파일 맨 앞의 `package` 문이 그 파일 안 모든 선언의 소속을 정하고, 같은 패키지면 다른 파일의 선언도 그대로 쓰고, 다른 패키지 것은 `import`한다. 다른 점은 **디렉터리 구조를 강제하지 않는다**는 것이다. 한 파일에 클래스를 여러 개 넣어도 되고 패키지와 폴더가 어긋나도 컴파일된다. 그래도 자바처럼 패키지대로 폴더를 맞추는 편이 낫다. 자바와 섞인 프로젝트면 더 그렇다.

## 루프와 대입만 빼면 제어 구조가 전부 값을 낸다

2장 전체를 가르는 구분이 식과 문이다.

- **식(expression)** — 값을 만든다. 다른 식의 일부로 들어갈 수 있다
- **문(statement)** — 자신을 둘러싼 가장 안쪽 블록의 최상위 요소로만 존재하고 값을 만들지 않는다

자바는 제어 구조가 전부 문이다. 코틀린은 루프(`for`, `while`, `do-while`)를 뺀 대부분이 식이다. 자바의 삼항 연산자 자리를 `if (a > b) a else b`가 그대로 맡고 `when`과 `try`의 결과도 바로 변수에 담는다. 2.5에 나오는 `throw`까지 식이라 `if (number in 0..100) number else throw IllegalArgumentException(...)`처럼 분기 한쪽에 예외를 둔다.

반대로 **대입은 항상 문이다.** `val alsoNumber = i = getNumber()`는 `Assignments are not expressions`로 컴파일되지 않는다. 대입이 값을 돌려주지 않으니, 비교(`==`)와 대입(`=`)을 헷갈리는 실수가 문법 단계에서 막힌다. 대입을 식으로 취급하는 자바·C에서는 흔한 실수다.

식이라는 성질이 함수 모양까지 바꾼다.

- **블록 본문 함수** — 본문을 중괄호로 감싼다. 반환 타입을 반드시 적고 값은 `return`으로 돌려준다
- **식 본문 함수** — 중괄호와 `return`을 빼고 등호 뒤에 식 하나만 둔다. `fun max(a: Int, b: Int): Int = if (a > b) a else b`. 반환 타입은 컴파일러가 식에서 추론하니 생략해도 된다

`if`나 `when` 분기에 블록을 쓰면 **블록의 마지막 식이 그 블록의 값이다.** `try`와 `catch` 블록도 같다. 이 규칙이 함수 본문 블록에는 없어서 헷갈리는데 이 장에 나온 두 함수가 그 경계를 그대로 보여준다.

```kotlin
fun evalWithLogging(e: Expr): Int =
	when (e) {
		is Num -> {
			println("num: ${e.value}")
			e.value
		}

		is Sum -> {
			val left = evalWithLogging(e.left)
			val right = evalWithLogging(e.right)
			println("sum: $left + $right")
			left + right
		}
		else -> throw IllegalArgumentException("Unknown expression")
	}
```

- `evalWithLogging`은 `= when (e) { ... }` 꼴의 식 본문 함수다. `is Num` 분기의 마지막 식 `e.value`와 `is Sum` 분기의 `left + right`가 분기의 값 → `when`의 값 → 함수의 반환값이 된다. `return`이 한 번도 안 나온다
- `fun max(a: Int, b: Int): Int { return if (a > b) a else b }`는 블록 본문 함수다. 여기서 `return`을 지우고 `if (a > b) a else b`만 남기면 마지막 식이 있어도 반환되지 않고 컴파일 오류가 난다

함수가 값을 내는 길은 둘뿐이다. 식 본문으로 쓰거나, 블록 안에 `return`을 두거나.

## `val`은 참조를 잠그고 `var`는 타입을 잠근다

변수 선언 키워드는 둘이다.

- **`val`**(value) — 읽기 전용 참조. 한 번만 대입되고 초기화한 뒤에는 다른 값을 대입할 수 없다
- **`var`**(variable) — 재대입 가능한 참조. 초기화한 뒤에도 다른 값을 대입할 수 있다

기본은 `val`이고 `var`는 꼭 필요할 때만 쓴다. 읽기 전용 참조와 변경 불가능한 객체를 부수 효과 없는 함수와 엮어야 함수형 스타일의 이득이 나오기 때문이다. 타입은 초기화 식에서 추론하니 보통 적지 않는다. 선언만 하고 나중에 대입하면 추론할 재료가 없어서 그때는 타입을 적어야 한다. `val`이라도 딱 한 번만 대입된다는 걸 컴파일러가 확인할 수 있으면, 조건에 따라 서로 다른 값으로 초기화해도 된다.

`val`이 잠그는 건 **참조**다. 참조가 가리키는 객체의 내부는 여전히 바뀐다. `val`로 받은 가변 리스트에 원소를 넣는 건 막히지 않고, 막히는 건 그 변수에 다른 리스트를 대입하는 것뿐이다. 참조를 복사해서 지켜주지도 않는다. `val b = a`는 객체를 복사하지 않고 같은 객체를 가리키는 참조를 하나 더 만드는 것이라 `b`로 리스트를 바꾸면 `a`로 봐도 바뀌어 있다. 내용까지 막으려면 변수가 아니라 객체 쪽을 바꿔야 한다. `mutableListOf` 대신 `listOf`로 만든 읽기 전용 리스트를 쓰는 식이다. 이것도 그 참조로 수정 메서드를 못 부르게 할 뿐 객체가 불변이라는 보장은 아니고 그 얘기는 3장 컬렉션에서 이어진다.

`var`는 값이 바뀌어도 **타입은 선언 시점에 고정된다.** 컴파일러는 초기화 식으로 타입을 정하고 이후 대입문마다 그 타입에 맞는지 검사한다. `Int`로 추론된 변수에 문자열을 넣으면 타입 불일치로 컴파일되지 않는다. 정적 타입 언어의 안전성과 성능을 지키려는 설계다. 다른 타입 값을 굳이 넣으려면 변환 함수를 쓰거나 강제로 형 변환해야 하는데, 그렇게까지 하는 건 안티패턴이다. 한 변수에 두 가지 뜻을 싣고 있다는 신호니 변수를 새로 만든다.

## 프로퍼티는 필드가 아니라 접근자 선언이다

자바에서 프로퍼티는 필드와 접근자(getter/setter)를 묶어 부르는 관례일 뿐 언어 기능이 아니다. 코틀린은 프로퍼티를 언어 기능으로 넣어서 그 조합을 완전히 대체한다.

- **`val` 프로퍼티** — 읽기 전용. 비공개 필드와 getter가 생긴다
- **`var` 프로퍼티** — 변경 가능. 비공개 필드와 getter, setter가 생긴다
- **사용** — `person.name`처럼 이름으로 읽으면 getter가, `person.isStudent = false`처럼 대입하면 setter가 불린다. `getName()`을 직접 부르지 않는다
- **뒷받침하는 필드(backing field)** — 대부분의 프로퍼티 뒤에는 값을 저장하는 필드가 있다
- **커스텀 접근자** — getter를 직접 정의하면 필드 없이 읽을 때마다 값을 계산하는 프로퍼티가 된다. `val isSquare: Boolean get() = height == width`

자바 쪽에서 보면 접근자라는 게 그대로 드러난다. `name`은 `getName()`이 된다. `is`로 시작하는 `isStudent`는 getter가 이름 그대로 `isStudent()`이고 setter는 `is`를 `set`으로 바꾼 `setStudent()`다. 거꾸로 자바 클래스의 getter/setter는 코틀린에서 `person.name`처럼 프로퍼티로 읽힌다. 그러니 `class Person(val name: String, var isStudent: Boolean)`은 필드 두 개를 만든 게 아니라 **접근자 세 개를 선언한 것이다.** 이 구분이 뒤에서 스마트 캐스트의 조건으로 돌아온다.

커스텀 getter 프로퍼티와 파라미터 없는 멤버 함수는 구현도 성능도 같다. 차이는 읽는 쪽이 받는 뜻뿐이다. **클래스의 특성을 기술하면 프로퍼티, 클래스의 행동을 정의하면 멤버 함수.** 정사각형인지는 사각형의 특성이라 `isSquare`는 프로퍼티다.

## `when`은 값·객체·조건·타입을 모두 분기 조건으로 받는 식이다

`when`의 재료는 이넘부터 나온다. 이넘은 `enum class`로 선언한다. `enum`은 `class` 앞에서만 뜻이 생기는 **소프트 키워드**라 다른 곳에서는 이름으로 써도 되고 `class`는 어디서든 키워드다. 이넘도 클래스라 상수마다 생성자 인자를 넘기고(`RED(255, 0, 0)`) 프로퍼티와 메서드를 둔다. 상수 목록과 메서드 사이에는 `;`가 필수다. 세미콜론을 생략하는 언어에서 줄바꿈으로 대신할 수 없는 드문 자리다. `import Color.*`로 상수를 임포트하면 `Color.` 없이 쓴다.

`when`을 자바 `switch`의 대체품으로만 보면 절반이 안 보인다. 분기 조건으로 받는 것이 훨씬 넓다.

- **이넘 상수** — `Color.RED -> "Richard"`. 분기 끝에 `break`가 없다. 맞은 분기 하나만 실행된다
- **한 분기에 여러 값** — `RED, ORANGE, YELLOW -> "warm"`. 쉼표로 묶는다
- **대상 캡처** — `when (val color = measureColor())`. `val color = ...` 줄을 따로 두지 않고 대상 값을 바로 변수에 담아 분기 안에서 그 변수의 프로퍼티(`color.r`)를 쓴다
- **임의의 객체** — `when (setOf(c1, c2)) { setOf(RED, YELLOW) -> ORANGE ... }`. 위에서부터 인자와 동등한(`==`) 분기를 찾는다. 집합은 원소 순서를 따지지 않으니 `RED, YELLOW`와 `YELLOW, RED`가 한 분기에 걸린다
- **인자 없는 when** — `when { 불리언 식 -> ... }`. 분기 조건이 불리언이면 된다. 비교할 때마다 `Set`을 만들지 않아 가비지가 안 생기지만 읽기는 어렵다
- **타입 검사** — `is Num -> e.value`. 아래 스마트 캐스트와 붙어 다닌다

식이라서 생기는 제약도 있다. 컴파일러가 **모든 경로에서 값이 나오는지** 검사한다. 이넘 상수를 전부 다루면 `else`가 필요 없고 하나라도 빠지면 `else`로 디폴트를 줘야 한다. `setOf` 비교나 인자 없는 `when`처럼 컴파일러가 조건을 따져볼 수 없으면 항상 `else`가 있어야 한다.

`is`로 타입을 검사하면 그 뒤로는 변수를 검사한 타입으로 바로 쓴다. 컴파일러가 캐스트를 대신 넣어주는 이것이 **스마트 캐스트**다. 자바에서 `instanceof`로 검사하고 다시 캐스트하던 두 단계가 하나로 줄었다. 직접 캐스트할 때는 `as`를 쓴다. 예제는 `Expr` 인터페이스를 `Num`과 `Sum`이 구현하는 식 트리다. `Expr`에는 메서드가 하나도 없다 — 여러 타입을 공통 타입 하나로 묶는 역할만 하는 이런 인터페이스를 **마커 인터페이스**라고 한다. `eval`은 `if` + `as` + `return` → 블록을 쓴 `if`-`else` 식 → 중괄호를 뺀 `if`-`else` 식 → `when` + `is` 순서로 줄어든다. 첫 모양과 마지막 모양만 놓으면 이렇다.

```kotlin
fun eval (e: Expr): Int {
	if (e is Num) {
		val n = e as Num
		return n.value
	}
	if (e is Sum) {
		 return eval(e.right) + eval(e.left)
	}
	throw IllegalArgumentException("Unknown expression")
}
// ...
fun eval(e: Expr): Int =
	when(e) {
		is Num -> e.value
		is Sum -> eval(e.right) + eval(e.left)
		else -> throw IllegalArgumentException("Unknown expression")
	}
```

첫 모양의 `e as Num`은 바로 위 `is` 검사로 스마트 캐스트가 이미 걸려 있어서 없어도 된다. 마지막 모양에서는 `is Num` 분기 안의 `e`가 곧 `Num`이다. `Expr`를 누가 또 구현할지 컴파일러가 모르니 마지막 모양에도 `else -> throw`가 남는다.

스마트 캐스트에는 조건이 하나 붙는다. **검사한 뒤 그 값이 바뀔 수 없어야 한다.** 검사와 사용 사이에 다른 값이 끼어들 수 있으면 캐스트를 보장하지 못한다. 클래스 프로퍼티라면

- `val`이어야 한다 — `var`는 검사와 사용 사이에 다른 코드가 재대입할 수 있다
- 커스텀 접근자가 없어야 한다 — getter는 호출이라 읽을 때마다 다른 값을 돌려줄 수 있다

"프로퍼티는 접근자 선언"이 여기서 돌아온다. 필드라면 한 번 읽은 값이 그대로지만 접근자는 두 번 부르면 두 번 계산된다.

## `for`의 `i++` 자리는 범위가 맡고, 같은 `in`이 소속 검사도 한다

`while`과 `do-while`은 자바와 같다. 새로운 건 **레이블**이다. 바깥 루프에 `outer@`를 붙이면 안쪽에서 `break@outer`로 바깥 루프를 빠져나가고 `continue@outer`로 바깥 루프의 다음 반복으로 넘어간다. 레이블 없는 `break`·`continue`는 늘 가장 안쪽 루프에 걸린다.

코틀린에는 `for (int i = 0; i < 10; i++)` 같은 고전 루프가 없다. 그 자리를 범위가 맡는다.

- **범위 `1..10`** — 시작과 끝을 `..`로 잇는다. 폐구간이라 끝 값 10도 들어간다
- **반개구간 `0..<size`** — 끝 값을 뺀다. 인덱스를 돌 때 쓴다
- **수열(progression)** — 범위의 값을 일정한 간격으로 차례로 돌 수 있으면 수열이다. `100 downTo 1`은 거꾸로 세고 `step 2`는 간격을 바꾼다
- **컬렉션 순회** — `for (color in collection)`
- **맵 순회** — `for ((letter, binary) in binaryReps)`. 키와 값을 두 변수로 풀어 받는다. 맵에 넣을 때도 `put` 대신 `binaryReps[char] = binary`처럼 대괄호를 쓴다
- **인덱스와 함께 순회** — `for ((index, element) in list.withIndex())`. 인덱스 변수를 따로 관리하지 않는다

`in`은 루프 밖에서는 소속 검사다. `c in 'a'..'z'`는 `'a' <= c && c <= 'z'`로 컴파일되고 `!in`은 그 반대다. `when` 분기 조건에도 `in '0'..'9' ->`처럼 들어간다. 범위는 숫자와 문자만의 것이 아니다 — 비교할 수 있는(`Comparable`) 값이면 범위를 만든다. `"Kotlin" in "Java".."Scala"`는 알파벳 순으로 두 문자열 사이에 있는지 묻는다. 컬렉션에도 `"Kotlin" in setOf("Java", "Scala")`처럼 쓴다. **순회도 소속 검사도 `in` 하나로 한다.**

## 코틀린은 체크 예외를 두지 않고, 무엇을 잡을지는 호출하는 쪽이 정한다

예외를 던지고 전파하는 방식은 자바와 같다. `throw`로 던지면 처리하는 코드를 만날 때까지 호출 스택을 거슬러 올라간다. `try`·`catch`·`finally`의 모양도 같다. 달라진 것은 두 가지다.

- **체크 예외와 언체크 예외를 구분하지 않는다.** 함수 시그니처에 `throws`를 적지 않고 호출하는 쪽도 잡을 의무가 없다. `reader.readLine()`은 자바라면 `IOException` 처리를 강제하지만 코틀린 컴파일러는 아무 말도 하지 않는다
- **`throw`와 `try`가 식이다.** `throw`는 분기 한쪽에 들어가고 `try`의 결과는 변수에 담는다. 이때 `try` 본문은 반드시 중괄호로 감싸고 블록의 마지막 식이 값이 된다

`val number = try { Integer.parseInt(reader.readLine()) } catch (e: NumberFormatException) { return }`에서 `catch`가 `return`하면 뒤 코드는 돌지 않고 함수가 끝난다. `return` 자리에 `null`을 두면 파싱에 실패했을 때 `number`가 `null`이 되고 실행은 이어진다. 앞 절의 "블록의 마지막 식이 값" 규칙이 `try`·`catch`에도 그대로 걸린다. 자바 7의 try-with-resources 같은 전용 문법은 없고 표준 라이브러리 함수 `use`가 그 자리를 맡는다.

체크 예외를 뺀 이유는 자바에서 얻은 경험이다. 자바는 처리를 강제했지만 실제로는 의미 없이 다시 던지거나 잡고 나서 무시하는 코드가 흔했다. 강제가 오류를 막지 못한 것이다. 코틀린은 그 강제를 걷어내고 무엇을 잡을지를 개발자에게 넘겼다. 대가는 분명하다. **컴파일러가 더는 알려주지 않으니, 무엇이 던져지는지는 읽는 쪽이 챙겨야 한다.**

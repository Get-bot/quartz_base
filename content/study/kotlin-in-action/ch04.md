## 이 장에서 남은 것

- 선언은 기본이 **`final`이고 `public`**이다. 자바와 반대로 상속은 `open`을 적은 곳만 열리고 오버라이드는 `override`를 적어야 컴파일된다.
- 내포 클래스는 **바깥 클래스 참조를 들고 있지 않다.** 자바의 `static` 내포 클래스가 기본이고 참조가 필요할 때만 `inner`를 붙인다.
- `sealed`로 하위 클래스를 닫아두면 **`when`에 `else`가 필요 없다.** 빠뜨린 분기는 컴파일러가 잡는다.
- `class User(val nickname: String)` 한 줄이 **생성자 파라미터와 프로퍼티와 초기화**를 같이 선언한다. `init`과 부 생성자는 이걸로 안 될 때만 꺼낸다.
- `data`는 `equals`·`hashCode`·`toString`·`copy`를, `by`는 위임 코드를 **컴파일러가 대신 쓴다.** `static`은 없고 그 자리는 동반 객체가 맡는다.

## 상속은 기본으로 잠겨 있고 열 곳에만 `open`을 적는다

자바는 `final`을 적지 않은 클래스를 누구나 상속한다. 코틀린은 반대다. 클래스도 메서드도 프로퍼티도 기본이 `final`이라 `open`을 적지 않으면 하위 클래스를 못 만들고 오버라이드도 못 한다. 이유는 **취약한 기반 클래스(fragile base class) 문제**다. 기반 클래스 구현을 바꿨더니 그 구현에 기대던 하위 클래스가 잘못 동작하는 경우다. 어디를 상속해도 되는지 기반 클래스가 밝혀두지 않으면 고칠 때마다 이 위험을 진다.

상속을 다루는 변경자는 넷이다.

- **`final`** — 오버라이드할 수 없다. 클래스 멤버의 기본값이라 보통 적지 않는다
- **`open`** — 오버라이드해도 된다. 상속을 허용할 클래스 앞에, 오버라이드를 허용할 메서드와 프로퍼티 앞에 하나씩 붙인다
- **`abstract`** — 반드시 오버라이드해야 한다. 추상 클래스는 인스턴스를 못 만든다. 추상 멤버는 구현이 없어서 누가 구현해야만 의미가 있으니 항상 열려 있고 `open`을 같이 적지 않는다
- **`override`** — 상위 클래스나 인터페이스의 멤버를 오버라이드한다는 표시. 자바의 `@Override`와 달리 빼면 컴파일되지 않는다. 오버라이드한 멤버는 기본이 열려 있어서 그 아래에서 더 못 바꾸게 하려면 `final override`로 잠근다

여닫는 단위는 클래스가 아니라 멤버다. `open class RichButton`에서 `open fun animate()`는 하위 클래스가 바꾸지만 `fun disable()`은 못 바꾼다. 클래스를 열었다고 멤버가 따라 열리지 않는다. 추상 클래스 안도 같다. `abstract`가 붙은 멤버만 열려 있고 추상이 아닌 함수와 프로퍼티는 `open`을 적지 않으면 닫혀 있다. **기반 클래스를 쓴 쪽이 열어둔 자리만 바뀐다.**

인터페이스는 처음부터 열려 있다.

- **디폴트 구현** — 추상 메서드뿐 아니라 본문이 있는 메서드도 둔다. 자바처럼 `default`를 붙이지 않고 본문만 쓴다. 구현하는 쪽은 그대로 쓰거나 새 동작으로 오버라이드한다
- **상태 없음** — 구현은 가져도 상태는 못 가진다
- **항상 `open`** — 인터페이스 멤버는 `final`로 바꿀 수 없다. 본문이 없으면 자동으로 추상 멤버다
- **콜론 하나** — 상속이든 구현이든 클래스 이름 뒤에 콜론을 찍고 상위 타입을 나열한다. `extends`와 `implements`를 나누지 않는다. 클래스는 하나만 확장하고 인터페이스는 여러 개 구현한다

여러 개를 구현하니 디폴트 구현끼리 부딪히는 경우가 생긴다. `Clickable`과 `Focusable`이 둘 다 `showOff()`의 디폴트 구현을 가지면 `ButtonV2`는 어느 쪽도 자동으로 물려받지 않는다. 오버라이드하지 않으면 컴파일 오류다. 하위 클래스가 `showOff()`를 직접 구현해야 하고 그 안에서 `super<Clickable>.showOff()`와 `super<Focusable>.showOff()`처럼 꺾쇠에 상위 타입을 적어 어느 구현을 부를지 고른다.

## 가시성은 `public`이 기본이고 패키지 전용 자리에는 모듈 단위 `internal`이 온다

가시성 변경자는 선언을 클래스 밖 어디까지 보여줄지 정한다. 구현에 대한 접근을 막아두면 그 클래스에 기대는 바깥 코드를 깨뜨리지 않고 안쪽을 고친다.

- **`public`** — 모든 곳에서 보인다. 아무것도 적지 않으면 이것이다
- **`internal`** — 같은 모듈 안에서만 보인다. 모듈은 한 번에 같이 컴파일되는 코틀린 파일 묶음이다
- **`protected`** — 그 클래스와 하위 클래스 안에서만 보인다. 최상위 선언에는 붙이지 못한다
- **`private`** — 클래스 멤버면 같은 클래스 안에서만, 최상위 선언이면 같은 파일 안에서만 보인다

자바와 갈리는 곳이 여럿이다. 기본값이 패키지 전용이 아니라 `public`이다. 패키지 전용 가시성은 아예 없고 그 자리에 `internal`이 있다. 패키지는 이름만 맞추면 밖에서도 그 안에 선언을 끼워 넣지만 모듈은 같이 컴파일되는 범위라 밖에서 끼어들지 못한다. `protected`도 좁다. 자바에서는 같은 패키지면 `protected` 멤버에 접근하지만 코틀린에서는 그 클래스와 하위 클래스뿐이다. 최상위 선언에 `private`을 붙이는 건 자바에 없던 것이다. 그 파일 안에서만 쓰는 함수나 클래스를 이렇게 숨긴다.

규칙이 하나 더 있다. **공개된 선언은 자기보다 덜 보이는 타입을 밖으로 내보내지 못한다.** 클래스의 기반 타입 목록과 타입 파라미터에 쓰인 타입은 그 클래스와 가시성이 같거나 더 높아야 하고, 메서드 시그니처에 쓰인 타입은 그 메서드와 같거나 더 높아야 한다. 아래 세 줄은 전부 컴파일 오류인데 이유가 다 다르다.

```kotlin
internal open class TalkativeButton {
    private fun yell() = println("SHIIII")
    protected fun whisper() = println("shh~~~")
}

fun TalkativeButton.giveSpeech() { // 오류: public 멤버가 자신의 internal 수신 타입인 TalkativeButton 노출
    yell() // 오류: TalkativeButton의 private 멤버
    whisper() // 오류: TalkativeButton의 protected 멤버
}
```

`giveSpeech`는 변경자가 없으니 `public`인데 수신 객체 타입 `TalkativeButton`은 `internal`이다. `public` 함수가 `internal` 타입을 노출하니 선언부터 막힌다. 함수를 `internal`로 낮추거나 클래스를 `public`으로 올려야 풀린다. `yell()`은 `private`이고 `whisper()`는 `protected`라서 안 된다. 3장에서 확장 함수는 클래스 밖의 정적 메서드라 비공개·보호 멤버를 못 쓴다고 한 그대로다. 확장 함수는 하위 클래스가 아니다.

바깥 클래스와 안쪽 클래스 사이도 자바와 다르다. 코틀린에서는 바깥 클래스가 자기 안에 선언된 내부 클래스나 내포 클래스의 `private` 멤버를 못 본다.

## 내포 클래스는 바깥 참조를 들지 않고, `sealed`는 하위 클래스 목록을 컴파일러에게 넘긴다

클래스 안에 클래스를 선언할 때의 기본값이 자바와 반대다.

- **내포 클래스(nested class)** — 변경자 없이 클래스 안에 선언한 클래스. 자바의 `static` 내포 클래스와 같다. 바깥 클래스 인스턴스에 대한 참조가 없다
- **내부 클래스(inner class)** — `inner`를 붙인 클래스. 바깥 인스턴스 참조를 들고 있다. 안에서 그 참조를 꺼낼 때는 `this@Outer`라고 쓴다

자바는 `static`을 안 붙이면 내부 클래스가 되고 바깥 인스턴스를 묵시적으로 붙든다. 책의 예는 `View`의 상태를 직렬화해 저장하는 코드다. `Button` 안에 `State`를 구현한 `ButtonState`를 두는데 `State`는 `Serializable`이다. 자바에서 `static`을 빼먹으면 `ButtonState`가 `Button`을 몰래 참조하고 `Button`은 직렬화가 안 되니 저장이 실패한다. 코틀린의 `class ButtonState : State`는 아무것도 안 붙인 쪽이 바깥 참조가 없는 쪽이다. **참조는 달라고 적었을 때만 생긴다.**

내포 클래스는 계층에 속한 클래스 수를 제한하고 싶을 때도 편하다. 그 제한을 언어가 직접 해주는 게 `sealed`다.

- **봉인된 클래스(sealed class)** — 상위 클래스에 `sealed`를 붙이면 그 클래스를 직접 상속하는 하위 클래스가 제한된다. 직접 하위 클래스는 컴파일 시점에 전부 알려져야 하고 봉인된 클래스와 같은 패키지, 같은 모듈 안에 있어야 한다
- **추상 클래스다** — `sealed` 변경자는 그 클래스가 추상 클래스라는 뜻도 담는다. `abstract`를 따로 적지 않는다
- **봉인된 인터페이스(sealed interface)** — 인터페이스에도 붙는다. 모듈이 컴파일되고 나면 바깥 모듈에서 새 구현을 더하지 못한다

쓸모는 `when`에서 드러난다. 2장의 `eval`은 `Expr`를 누가 또 구현할지 컴파일러가 몰라서 `else -> throw`를 달고 있었다. `sealed class Expr`로 바꾸면 하위 클래스가 `Num`과 `Sum`뿐이라는 걸 컴파일러가 안다. `is Num`과 `is Sum` 두 분기만 쓰면 `else`가 없어도 컴파일되고 모든 분기를 처리했는지는 컴파일러가 확인한다. 나중에 하위 클래스를 하나 더하면 그걸 처리하지 않은 `when`은 컴파일되지 않는다. **`else`가 삼키던 빠진 분기가 컴파일 오류로 올라온다.**

## 주 생성자 한 줄이 파라미터와 프로퍼티와 초기화를 같이 선언한다

생성자가 둘로 나뉜다.

- **주 생성자(primary constructor)** — 클래스 이름 뒤 괄호 안에 선언한다. 생성자 파라미터를 지정하고 그 파라미터로 초기화되는 프로퍼티를 정의한다. 클래스 본문 밖에 있고 코드는 담지 못한다
- **초기화 블록(initializer block)** — `init`으로 시작하는 블록. 객체가 만들어질 때 실행될 코드를 담는다. 주 생성자가 코드를 못 담으니 같이 쓴다. 여러 개 선언해도 된다
- **부 생성자(secondary constructor)** — 클래스 본문 안에 `constructor`로 선언한다

`User`를 가장 풀어 쓴 모양과 가장 줄인 모양이다.

```kotlin
class User constructor(
    _nickname: String,  // 주 생성자
) {
    val nickname: String

    init {  // 초기화 블록
        nickname = _nickname
    }
}

// ...

class User(val nickname: String)
```

사이에 두 단계가 있다. 파라미터 이름의 `_`는 프로퍼티와 구분하려고 붙인 것이라 이름을 같게 두고 `this.nickname = nickname`으로 써도 된다. 다음은 `init`을 없애고 프로퍼티 선언에서 `val nickname: String = _nickname`으로 바로 초기화한다. 주 생성자 파라미터는 프로퍼티 초기화 식과 초기화 블록 안에서만 보이니, 이 두 자리가 파라미터를 프로퍼티로 옮기는 곳이다. 마지막으로 파라미터 앞에 `val`을 붙이면 **파라미터 선언이 곧 프로퍼티 선언**이 된다. 변경자가 없는 주 생성자는 `constructor` 키워드도 뺀다.

나머지 규칙도 짧은 쪽이 기본이다.

- **기본값** — 생성자 파라미터에도 `val isSubscribed: Boolean = true`처럼 기본값을 준다
- **`new` 없음** — `User("hands")`처럼 생성자를 함수처럼 바로 부른다
- **상위 클래스 초기화** — 기반 클래스 이름 뒤에 괄호를 치고 인자를 넘긴다. `class SocialUser(nickname: String): User(nickname)`
- **디폴트 생성자** — 생성자를 하나도 선언하지 않으면 인자 없는 생성자를 컴파일러가 만든다. 그래도 하위 클래스는 상위 생성자를 반드시 불러야 해서 `class RadioButton: Button()`처럼 빈 괄호가 붙는다
- **비공개 생성자** — `class Secretive private constructor(...)`. 클래스 밖에서 인스턴스를 못 만든다. 팩토리 함수로만 만들게 할 때 쓴다

인터페이스에는 생성자가 없으니 상위 타입 목록에서 이름 뒤에 괄호가 없다. **괄호가 있으면 클래스, 없으면 인터페이스다.**

부 생성자는 쓸 일이 드물다. 자바에서 생성자를 여러 개 오버로드하던 이유는 대부분 인자 기본값이었고 그건 주 생성자 시그니처에 기본값을 적으면 끝난다. 남는 경우는 상위 클래스에 생성자가 여럿이고 그걸 그대로 받아야 할 때다. `Downloader`가 `String?`을 받는 생성자와 `URI?`를 받는 생성자를 따로 갖고 있으면 `MyDownloader`도 부 생성자 둘을 선언하고 각각 `super(url)`, `super(uri)`로 상위 생성자에 넘긴다. `constructor(url: String?) : this(URI(url))`처럼 `this`로 같은 클래스의 다른 생성자에 넘겨도 된다. 이때는 주 생성자가 없으니 `class MyDownloader : Downloader`에 괄호가 없다.

프로퍼티 쪽에서 뻔하지 않은 건 값이 어디에 저장되느냐다. 인터페이스에 `val nickname: String`을 선언하면 추상 프로퍼티가 된다. 인터페이스는 상태가 없으니 필드를 두라는 말이 아니다. 구현하는 클래스가 그 값을 얻을 방법을 내놓으라는 뜻이고 방법은 클래스마다 다르다.

- **주 생성자에서 바로** — `class PrivateUser(override val nickname: String)`. 생성자 파라미터가 곧 오버라이드한 프로퍼티다
- **커스텀 게터** — `SubscribingUser`는 `get() = email.substringBefore('@')`. 필드 없이 읽을 때마다 계산한다
- **초기화 식** — 객체를 만들 때 한 번 계산해 필드에 넣어둔다. 계산이 비싸면 게터가 아니라 이쪽이다

인터페이스 안에 게터가 있는 프로퍼티도 둔다. `EmailUser`의 `nickname`은 `email`에서 계산하는 게터를 인터페이스가 직접 갖고 있어서 구현 클래스는 `email`만 오버라이드한다. 이것도 상태는 없고 매번 다시 계산한다.

값을 저장하면서 접근할 때 하는 일도 바꾸고 싶으면 접근자 안에서 필드를 직접 만진다.

- **뒷받침하는 필드(backing field)** — 프로퍼티 값을 실제로 담는 필드. 접근자 본문에서 `field`라는 식별자로 접근한다. 게터에서는 읽기만 하고 세터에서는 읽고 쓴다
- **필드가 생기는 조건** — 컴파일러는 접근자가 `field`를 쓰는 프로퍼티에만 필드를 만든다. 기본 접근자도 `field`를 쓰는 셈이다. `field`를 안 쓰는 커스텀 접근자만 있으면 필드가 없다
- **접근자 가시성** — 기본은 프로퍼티와 같다. `get`이나 `set` 앞에 변경자를 적어 바꾼다

`address`의 세터는 `"$field" -> $value`로 바뀌기 전 값과 새 값을 찍고 `field = value`로 저장한다. 쓰는 쪽은 `user.address = "new Value"`라는 평범한 대입 그대로다. `var`의 게터와 세터 중 한쪽만 정의해도 되니 게터는 기본 구현이 남는다. `LengthCounter`의 `counter`는 `private set`이라 밖에서는 읽기만 하고 값은 `addWord`만 바꾼다. **프로퍼티는 공개하고 바꾸는 길만 닫는다.**

## `data`와 `by`는 손으로 쓰던 메서드를 컴파일러에게 넘긴다

값을 담는 클래스라면 자바에서든 코틀린에서든 세 메서드를 오버라이드하게 된다.

- **`toString()`** — 문자열 표현
- **`equals()`** — 객체의 동등성. 코틀린의 `==`는 참조가 같은지가 아니라 `equals`를 불러 값이 같은지를 본다. 참조 비교는 `===`다
- **`hashCode()`** — 해시 컨테이너가 쓰는 값. `equals`가 같다고 한 두 객체는 해시 코드도 같아야 `HashSet`이나 `HashMap`에서 제대로 찾아진다

`data` 변경자를 붙이면 이 메서드들을 컴파일러가 만든다.

- **`equals`** — 주 생성자에 선언된 모든 프로퍼티의 값이 같은지 본다
- **`hashCode`** — 주 생성자의 모든 프로퍼티의 해시 값으로 계산한 값을 돌려준다
- **`toString`** — 필드를 선언 순서대로 나열한다. `Customer(name=Sam, postalCode=11521)`
- **`copy`** — 객체를 복사하면서 일부 프로퍼티만 바꾼다

기준은 **주 생성자에 선언한 프로퍼티뿐**이다. 클래스 본문에 선언한 프로퍼티는 `equals`와 `hashCode` 계산에 들어가지 않는다. 그래서 `Customer("Sam", 11521)` 두 개는 서로 다른 인스턴스인데도 `==`가 `true`이고 `hashCode()`도 같다.

`copy`가 있는 이유는 불변성이다. 책은 데이터 클래스의 프로퍼티를 전부 `val`로 두라고 권한다. `HashMap` 같은 컨테이너에 키로 넣은 객체의 프로퍼티를 바꾸면 컨테이너 상태가 어긋난다. 바꿀 일이 생기면 원본을 고치지 않고 `copy`로 일부만 다른 복사본을 만든다. 손으로 구현하면 `fun copy(name: String = this.name, postalCode: Int = this.postalCode) = Customer(name, postalCode)` 꼴이다. 파라미터 기본값이 전부 현재 값이라 바꿀 것만 이름을 붙여 넘긴다. 복사본은 원본과 생명주기가 달라서 값을 바꾸거나 버려도 원본을 참조하는 쪽에 영향이 없다.

`by`는 다른 종류의 반복을 없앤다. 상속이 기본으로 막혀 있으니 상속할 수 없는 클래스에 동작을 더할 일이 생기고 그때 쓰는 게 데코레이터 패턴이다.

- **데코레이터 패턴** — 기존 클래스 대신 쓸 새 클래스를 만들되 같은 인터페이스를 구현하고 기존 클래스를 내부 필드로 들고 있다. 새 기능은 데코레이터의 메서드로 새로 정의하고, 그대로 필요한 기능은 데코레이터의 메서드가 기존 객체에 요청을 전달한다
- **클래스 위임(class delegation)** — 상위 타입 목록의 인터페이스 이름 뒤에 `by`와 객체를 적으면 그 인터페이스의 구현을 그 객체에 위임한다. 전달만 하는 메서드는 컴파일러가 만든다

문제는 전달하는 코드다. 인터페이스에 메서드가 열 개면 넘기기만 하는 메서드 열 개를 손으로 써야 한다. `class DelegatingCollection<T>(innerList: Collection<T> = mutableListOf<T>()) : Collection<T> by innerList`는 그 전부를 `by innerList`로 끝낸다. 바꾸고 싶은 메서드만 오버라이드한다.

```kotlin
class CountingSet<T>(
    private val innerSet: MutableCollection<T> = hashSetOf(),
) : MutableCollection<T> by innerSet {
    var objectsAdded = 0

    override fun add(element: T): Boolean {
        objectsAdded++
        return innerSet.add(element)
    }

    override fun addAll(elements: Collection<T>): Boolean {
        objectsAdded += elements.size
        return innerSet.addAll(elements)
    }
}
```

`CountingSet`은 `add`와 `addAll`만 직접 구현해 원소를 몇 번 넣으려 했는지 세고, 나머지 `MutableCollection` 메서드는 전부 `innerSet`으로 넘어간다. **상속이 아니라서 `innerSet`의 구현 방식에 묶이지 않는다.** `CountingSet`이 기대는 건 `innerSet`의 공개 API뿐이고 요청을 중계할 뿐이다. `final`을 기본으로 둔 이유가 구현에 기대는 하위 클래스였는데 위임에는 그 의존이 없다.

## `object`는 클래스 선언과 인스턴스 생성을 한 번에 하고, `static` 자리는 동반 객체가 맡는다

`object` 키워드는 세 군데에서 쓰이고 셋 다 클래스를 정의하면서 그 인스턴스를 같이 만든다.

- **객체 선언(object declaration)** — 싱글턴을 정의한다
- **동반 객체(companion object)** — 어떤 클래스와 관련은 있지만 부르는 데 그 클래스의 인스턴스가 필요 없는 메서드와 팩토리 메서드를 담는다. 멤버에는 바깥 클래스 이름으로 접근한다
- **객체 식(object expression)** — 자바의 익명 내부 클래스 자리에 쓴다

객체 선언은 클래스 선언과 그 클래스의 단일 인스턴스 선언을 합친 것이다. `object Payroll`이라고 쓰면 싱글턴 패턴을 손으로 짤 필요가 없고 `Payroll.allEmployees`, `Payroll.calculateSalary()`처럼 이름 뒤에 점을 찍어 쓴다. 선언한 자리에서 생성자 호출 없이 바로 만들어지니 **생성자를 쓸 수 없다.** 초기 상태가 필요하면 본문에 직접 적는다. 그 밖에는 보통 클래스와 같다.

- **상속** — 클래스를 상속하거나 인터페이스를 구현한다. `object CaseInsensitiveFileComparator : Comparator<File>`처럼 프레임워크가 요구하는 인터페이스를 구현해야 하는데 상태는 필요 없을 때 맞는다
- **값으로 쓰기** — 일반 객체를 쓰는 자리에는 어디든 쓴다. 상위 인터페이스 타입으로 받아 함수 인자로 넘긴다
- **클래스 안에 선언** — `Person` 안의 `object NameComparator`. 바깥 클래스 인스턴스가 몇 개든 이 객체는 하나다

코틀린 클래스에는 정적 멤버가 없다. `static` 키워드가 없고 그 자리를 패키지 수준 최상위 함수와 객체 선언이 나눠 맡는다. 대부분은 최상위 함수로 충분한데 최상위 함수는 클래스의 `private` 멤버를 못 본다. 인스턴스 없이 불러야 하면서 클래스 안쪽 정보에 닿아야 하는 함수가 갈 곳이 동반 객체다. 팩토리 메서드가 대표적이다. 클래스 안에 `companion object`를 두면 그 멤버를 `Person.fromJson()`처럼 클래스 이름으로 부른다. 자바의 정적 메서드 호출과 같은 모양이다. 다만 동반 객체는 클래스에 속하지 인스턴스에 속하지 않아서 `myObject.callMe()`처럼 인스턴스로는 못 부른다.

동반 객체는 자신을 둘러싼 클래스의 `private` 멤버를 전부 본다. `private` 생성자도 부른다. `class User private constructor(val nickname: String)`로 생성자를 막고 동반 객체에 `newSubscribingUser(email)`과 `newSocialUser(accountId)`를 두면 밖에서는 이 팩토리 메서드로만 `User`를 만든다. **생성자는 이름이 하나뿐이지만 팩토리 메서드는 목적대로 이름을 붙인다.**

동반 객체는 문법이 특별해 보여도 클래스 안에 정의된 일반 객체다. 그래서 일반 객체가 하는 걸 다 한다.

- **이름** — `companion object Loader`처럼 이름을 붙인다. `Person.Loader.fromJson()`과 `Person.fromJson()` 둘 다 된다. 안 붙이면 이름은 `Companion`이다
- **인터페이스 구현** — `companion object : JSONFactory<Person>`. 이러면 `loadFromJSON(Person)`처럼 클래스 이름을 그 인터페이스의 인스턴스로 넘긴다. 실제로 넘어가는 건 `Person`의 동반 객체다
- **확장 함수** — `fun Person.Companion.fromJson(...)`. 동반 객체에 확장을 붙이면 `Person.fromJson(...)`으로 부른다. 멤버처럼 보여도 멤버가 아니다. 붙일 대상이 있어야 하니 비어 있더라도 `companion object {}`를 선언해 둔다

확장으로 빼는 이유는 관심사 분리다. 역직렬화 같은 함수를 `Person` 본문에 두지 않고 클라이언트/서버 통신 모듈 쪽에 선언한다.

객체 식은 이름 없는 객체다. `object : MouseListener { ... }`는 클래스를 정의하고 그 인스턴스를 만들지만 클래스에도 인스턴스에도 이름을 붙이지 않는다. 자바 익명 내부 클래스보다 하는 일이 많다.

- 인터페이스를 여러 개 구현해도 되고 하나도 구현하지 않아도 된다
- 식을 감싼 함수의 변수에 접근한다. `final`이 아닌 변수도 쓰고 값도 바꾼다. `var clickCount`를 객체 식 안의 `onClick()`에서 `clickCount++`로 올린다

객체 선언과 달리 싱글턴이 아니다. 식이 실행될 때마다 새 인스턴스가 생긴다. 오버라이드할 메서드가 여럿일 때 쓸모가 있다.

## 인라인 클래스는 객체를 만들지 않고 타입만 하나 더 세운다

`Int` 하나만 봐서는 그 값의 단위가 무엇인지 모른다. 클래스로 감싸면 타입이 의미를 말해주고 엉뚱한 값을 넘기는 걸 컴파일러가 막는다. 대가는 객체다. 값마다 감싸는 객체를 만들고 가비지 컬렉터가 치워야 한다. 인라인 클래스는 그 비용 없이 타입 안전성만 남긴다.

- **선언** — `@JvmInline` 애너테이션과 `value class`. `@JvmInline value class UsdCent(val amount: Int)`
- **인라인** — 실행 시점에 인스턴스가 감싼 프로퍼티로 대체된다. 클래스의 데이터가 쓰이는 자리에 그대로 들어간다
- **조건** — 프로퍼티가 하나뿐이어야 하고 주 생성자에서 초기화해야 한다
- **계층 밖** — 다른 클래스를 상속하지 못하고 상속되지도 않는다
- **그래도 되는 것** — 인터페이스 구현, 메서드 정의, 계산된 프로퍼티. `UsdCent`가 `PrettyPrintable`을 구현하고 `val salesTax get() = amount * 0.06`을 갖는다

**소스에서는 타입이고 실행할 때는 `Int`다.** 그래서 기본 타입 값의 의미를 분명히 하고 싶을 때 주로 쓴다.
